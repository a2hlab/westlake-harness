# CLAUDE.md — 西湖 adapter（AOSP-on-OH）工作铁律

> 来源：`/opt/10.Project/16-WestLake/16.12-HanBing/adapter/doc/` 设计文档（overall_design / build and deployment / content_provider_datashare / liboh_android_runtime / interface_bridge / appspawn_x）。
> **这些是 HanBing 的设计铁律，任何 adapter 修订必须严格遵守。违反即为跑偏。**

## 铁律 1 — libart 是固定稳定基座，禁止改 ART 内部

- libart = **"一次构建、长期复用的稳定基座"**，是通用 DEX 执行引擎，**不含任何应用层代码**。
- **唯一允许的 libart 源改 = musl-compat**（如 `libcxx-ohos array<T,0>::data()` fix）、libandroid_runtime trim、libbionic_compat 增补、OH musl ABI 适配。
- **严禁 class_linker / vtable / entrypoint 算法补丁**。`FIX-VTABLE-A` 家族（vtable 重定位、entrypoint-coherence、proxy-entrypoint-coherence、iftable、postpass）**属于禁区，不得新增、应逐步移除**。
- 若怀疑是 ART-on-musl 基座 bug（设计唯一允许重编 libart 的类别）→ **最小化在 base 修**，不是 vtable 重定位。

## 铁律 2 — Android Framework 完整保留

- BCP（`core-libart` / `framework` 等）内 Java 代码**不改语义、不删类、不改方法体**。
- **反例（明令禁止）**：改 `ActivityThread` 内部逻辑；删 AOSP class 来"少一个 NoClassDefFoundError"。

## 铁律 3 — 只在 IPC 边界处适配，绕开 ART

- 适配发生在 **IPC 边界**，路由到 OH 服务，**不在 ART 内部**。
- 所有适配修复必须落在：**`liboh_android_runtime.so` / `liboh_adapter_bridge.so` / `aosp_patches`(musl-compat)**——不在 class_linker / vtable。
- register_X 只做运行时 `FindClass` 这类查找，**与 boot image AOT 缓存正交**。

## 铁律 4 — boot 连贯性（设计强制，可做）

- **任何 BCP jar 字节变化 → 27 段 boot 全量重烤**（boot image 锁定）。
- **推送任何 BCP jar / boot 段后，必须 27 段全推**，否则 ART `ValidateOatFile` 拒载 → `InitWithoutImage` abort。
- **dex2oat 与 libart 必须同 ART build 配置**（`asm_defines.h` Thread offset 不得跨 arch 泄漏；ARM32=0x4 / ARM64=0x8 物理隔离树，永不 swap）。
- libart 改动 ⇒ 必须配套连贯 boot 重烤（同源 dex2oat + boot.art）。

## 铁律 5 — 验证纪律

- **truly-cold 才认**：reboot 后第一个冷 fork + NO_JIT（`APPSPAWNX_NO_JIT=1`）；warm fork 一律视为假象。
- **编译/链接 ≠ 跑通**；daemon Listening（loader 连贯）≠ AOT 入口连贯。

## 设备与树隔离

- **D200 = arm32**（`/data/aosp`，POINTER_SIZE 0x4，lib/，framework/arm）；**D600 = arm64**（`/data/aosp-arm64-d600`，0x8，lib64/，framework/arm64）。两树物理隔离，命令带 `--aosp-root` 决定，**D600 构建永不读 /data/aosp、永不验证 D200**。
- 多台同型设备时**只动自己被指派的那台**（如 D600 只动 `-t 5583`，绝不碰 `5bb5b1ae`）。
