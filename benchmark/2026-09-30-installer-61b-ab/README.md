# 61b installer-only background-launch A/B

A successful StartAbility return was previously being conflated with permission to activate the next window. The old installer left START_ABILITIES_FROM_BACKGROUND absent. This experiment installs the accepted 6aadb8b4/7048c7c5 pair, pins r17p a0ed5c4f, and observes the actual WMS decision separately from screenshots. No native or graphics version is changed.

## Inputs and scope

- Source deployment recipe: `../2026-09-30-installer-background-launcher/HANDOFF.md`; unchanged accepted binaries. The local deployment copy changes only serial, lane and transaction directories.
- Board: `61b0657200000000000000000324012c`, exclusively locked by cx-t0 after cc-t3 released it. Lock-time `original.json` records r17p already restored by cc-t3.
- Original native package: v3c 668e4f7c; CommonEvent runtime 9e14bf20 and HWUI be59260f retained. No graphics 32df or next-series candidate is used.
- Fixed JAR: r17p `a0ed5c4fedd952762256a24ab7801deb3ad6e696a0204853ce5000316336d173`.
- Old installer: libbms 6f94d4f4 / libapk_installer eb6824b4. New: 6aadb8b4 / 7048c7c5. Both system and platformsdk copies are backed up and verified through the foundation root.
- Baseline: original r17p 61b sweep, with trace extraction from cx-bms comparison commit 36529f13. `permission_evidence.py` copies that extractor; grant, actual linked WMS allow and visual outcome remain separate fields.
- Seventeen requested keys, original APKs, master bms_batch `--reinstall --hilog 20 --shots 5,20 --focus-check`. Predictions were recorded before execution.

## Recovery and limits

Foundation restart produced an actually black screenshot despite correct service-library hashes. Following the announced recovery, only 61b rebooted (6fd44228 → 58aef9fc); USB reconnected automatically. The exact original v3c package was replayed without `--upgrade`, then r17p was restored. Two missing original ZigZag prerequisite files were restored from the old staged payload after exact SHA verification; no replacement version was introduced. See `replay-prereqs/receipt.json` and recovery logs. The first replay and first JAR pin refused before their respective changes (missing mount target; live HelloWorld child).

Reboot, fresh app state and launch order are covariates: fixed runtime bytes do not establish single-factor causality for every UI change. The installer also contains SelectLauncherActivity; per-app old/new launchers are recorded. Strong permission evidence requires the same nativeStartAbility/NotifySCB trace and WMS allow, not generic WMS traffic from another package.

The first batch stopped during post-screenshot FitoTrack collection with `HDC lost remote status marker`. Boot ID and all guarded runtime hashes were unchanged on reconnect. The original record is retained. A fresh run repeats FitoTrack and completes the remaining ten keys. `combine_runs.py` refuses different fingerprints and selects exactly one completed record per requested key; `facts.txt` is generated by the unchanged master facts function. Both source runs remain available on Mac.

## Verified example

Wikipedia's onboarding activation trace `a92ab1452aeed8d` now reaches `canStartAbilityFromBackground:1` (07:09:30.983). It subsequently hits the unchanged HWUI assertion at 07:09:32.818: `ASSERT FAILED cond=mEglSurface == EGL_NO_SURFACE msg=drawRenderNode called on a context with no surface!`; t20 is the OH desktop. This verifies permission progress and does not claim Wikipedia is lit.
