## Record and failure semantics

`filesDir/launch-observation.json` is separate from the unchanged `window-state.json`. A UUID generated by the SDK util API identifies a loaded JS instance; a shared monotonically increasing sequence distinguishes callbacks, including callbacks on multiple Ability objects in that instance. Failed write attempts consume sequence numbers. Two timestamps may be identical. UUID is an observational token, not an authenticated PID/birth identity, and module reload can create another token in the same OS process. Neither token nor time grants authority.

Records contain only callback, instance, sequence, time, numeric `launchReason`, classified `launchReasonMessage`, home action/entity classes and the two fixed non-authority fields. Missing/invalid fields are `unknown`. Only LaunchParam supplies reasons: Want.parameters, URI and caller fields are never read. Own data properties are read without invoking getters; invalid objects/proxies are handled conservatively. Entity scanning is bounded to16 entries and each emitted JSON record is bounded to1024 ASCII bytes.

Local SDK `AbilityConstant.REASON_MESSAGE_DESKTOP_SHORTCUT` supplies the exact string `ReasonMessage_DesktopShortcut` (API20); it maps only to `desktop_shortcut`. Other messages remain `unknown`. SDK `ohos.want.action.home` and the checked-in host module's `action.system.home` both map to `home`; entity matching is exact `entity.system.home`. These vocabularies do not establish that any actual icon Want contains them. The generic module is cited for the literal only, not as the installed T32 module. SDK excerpts and original hashes are retained. The OH6.0 documentation URL supplied by outer is background reference only; no network fetch or additional document-content claim was made.

Each callback writes a same-directory temporary file, requires a complete byte count, closes, then renames to the final record. Success is logged only after rename returns. Open/write/short-write/close/rename errors preserve the prior committed record and produce a fixed failure phase, never exception text or input strings. Failure cleanup is best effort; rename and close with unknown outcomes are not repeated. A failed cleanup may leave a temporary file, which is never a committed observation. File commit remains authoritative if hilog itself fails. This is atomic visibility design, not fsync-based power-loss durability or real-device filesystem validation.

## Offline verification

Node vm loads the actual generated EntryAbility and invokes every production callback, including the function registered by `stage.on`. It compares window writes/logs to the exact baseline. Tests cover both home spellings, bounded reasons, absent/malformed inputs, secrets in all temporary/final written bytes and logs, each I/O failure, UUID failure, equal timestamps, multiple contexts/Ability objects, and logging failure. It uses filesystem/UI mocks, not a replacement observation model. `tools/spec-checks/tests/toutiao_host_launch_observation.rs` calls this checker.
