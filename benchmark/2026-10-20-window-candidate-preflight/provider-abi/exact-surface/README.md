The previous profile established source declarations but could not prove native-buffer ownership or Abort error handling for the returned firmware object. This pass narrows those unknowns using **8 unique functions**, REA/Ghidra 12.1.4 and independent LLVM disassembly of the same ELF. It does not turn a source profile into a deployed provider or a video-playback result.

## Still unknown: handle fields and actual execution

The eight boundary functions do not dereference BufferHandle contents. They establish neither the six signed32 prefix fields, nor whether the handle has the older `key` member, nor actual size/stride/format values. The two original headers retained under `../source-profile/` remain **profiles**, with layouts 56 versus 64 bytes; `oh61_buffer_handle.h` in the source-build snapshot asserts the 56-byte build profile but is not a measurement of this provider. Stride-byte semantics are documented by archived headers; the returned provider's field offset/value and pixel-size relation still need exact evidence. Do not promote any BufferHandle field or lifetime fact merely because a newer/local header compiles.

The next narrowly authorized offline step, if needed, is to examine exact SurfaceBufferImpl field getters/CloneBufferHandle and Map/Unmap internals against this same SHA. It was deliberately not added to this pass's 8-function limit. Actual execution evidence must independently tie dlsym result + load bias + namespace to the provider SHA, validate the unwrap/input object's identity and vtable, then observe request/handle/map/fence/unmap/flush outcomes under an admitted window. Public Abort success alone cannot establish lower queue release. No such runtime evidence is claimed here.
