# Task Contract: Seal the demo board

## Intent
把演示板封存成以后固定拿来展示的机器:记下完整指纹,写一份照着就能演示的手册和一键恢复脚本,并在仓库规则里把它登记为演示板。

## Must
- 只用一块 D600 做演示板,由 t1 按证据选定并在黑板登记序列号;另两块板保持统一态实验板,本计划不改它们。
- 演示板的最终状态必须是一个有记录的版本:runtime-fingerprint 逐件可查,`check_frozen.py` 0 违规;在统一态之上加的东西(头条等)一律单文件叠加、带回滚脚本,不整代重建。
- 截图是地面真相。计数一律贴运行目录 `facts.txt` 或 `run_facts.py` 的原样输出;数不出来写 unknown。
- 「点亮」只按启动后约 20 秒截图里是应用自己的界面判;首屏空列表、加载中、带错误框分列,不算进 100+。
- 板子纪律照 AGENTS.md:写操作前先只读检查;每块板同一时刻一个上板任务;单项实验 ≤30 分钟,批量 ≤45 分钟,用完即释放锁。
- 静态优先:路径、命名空间、部署件内容这类问题先离线扫描再上板。
- 交件只走 `land.py`;不推送;不提交密码、服务器账号。
- 封存(t5)之后,演示板零改动,心跳只做只读巡检;解封只有用户能批。

## Decisions
- 范围:不再新点亮。现有 128 个照旧:演示手册里亮的 112 个演示,半亮/不亮的 16 个留附录不修。全力只做三件:128 个可演示、BoatAttack 可玩、头条可交互。
- BoatAttack 可玩 = t2b 判据:横屏 1920×1200 满屏、HUD 清晰不拉伸、颜色正常不偏紫、加速后 KPH 到两位数且圈数推进、转向有效,与原版 PASS 画面并排对照。
- 头条可交互 = 前台桌面点击能启动、能刷首页、能点开文章。
- 硬要求:拔电重启后不接 Mac 也能演示(开机自启),三者都算。
- 冻结底线:为 Boat 与渲染修复重编的共享件(liboh_adapter_bridge、liboh_android_runtime、oh-adapter-runtime.jar)可以替换冻结项,条件 = 重启后全量 128 回归(t4/regress_vs_signoff.py)不退步,并在 knowledge/frozen/frozen.json 登记新版本(原因、对照、重验证据、全量路径)后再部署。演示板解封已批,封存前可写。
- 封存两步:v1 = 128 + 头条 + 自启;Boat 达标后重封 v2;每次封存只重启一次,重启前先拍快照并过 sepolicy 门。
- 指纹包含 runtime-fingerprint、叠加清单、已装包列表(包名+版本+APK SHA)、系统版本,存进 benchmark 目录。
- 演示手册写:开机后怎么确认就绪、演示顺序、头条怎么操作、某个应用失败时跳过哪个;一键只读自检脚本对比当前指纹与封存指纹。
- 恢复脚本从封存的部署件把板恢复到封存态,先在空闲板上演练一次。
- AGENTS.md 板子纪律加一行:该序列号为演示板,零改动,只读巡检,解封只有用户能批。
- 分两步封存(用户 2026-10-10 定):先封 v1 = 统一态 128 个 app + 头条 Route B + 开机自启(拔电重开即可演示),不带 BoatAttack;Boat 作为叠加层做好后再补进去重封 v2。演示版不被 Boat 卡住。
- 61b 最终重启前严格执行「先拍快照(board_state_snapshot.py),再跑 sepolicy 门(t2d,配方每条有策略证明)」,有推演器(t2e)就附预测表;任何一项不过不重启(用户 2026-10-10 定)。
- 每次封存只重启一次:该版的所有层(自启、头条、以及 v2 的 Boat)一次叠齐,重启前按 RUNBOOK 拍完整状态快照,重启后不碰 Mac 自起,再跑全量 128 回归(t4/regress_vs_signoff.py)。
- 用户 2026-10-12 明示「同意精确参数派生，继续封板」：同板重启及备机恢复允许白名单中的宿主 UID/GID、序列号、独立控制目录和宿主窗口 ID 按实测参数精确派生；固定模板 SHA、生成器 SHA、输入参数、逐项差异和完整生成文件 SHA，其他字节必须相等，未知差异拒绝。原 seal 保留不覆盖，派生证明单独绑定它；不以任意文件排除或空白例外满足验收。

## Boundaries

## Completion Criteria
Scenario: Self check matches the sealed fingerprint
  Test:
    Filter: demo_baseline_seal
  Given The board is sealed and the fingerprint is stored
  When demo_selfcheck.sh runs read-only
  Then It reports every component equal to the sealed fingerprint or its user-approved exact parameter realization and exits zero and any unapproved difference exits nonzero naming the component

Scenario: Restore is rehearsed on a spare board
  Test:
    Filter: demo_baseline_seal
  Given A spare board starts from the unified state
  When demo_restore.sh runs
  Then The spare board self check matches the original fingerprint through the user-approved exact parameter realization with template and generator hashes parameters complete rendered file hashes and retained raw execution logs

Scenario: Self check detects drift
  Test:
    Filter: demo_baseline_seal
  Given One deployed file differs from the sealed fingerprint
  When demo_selfcheck.sh runs
  Then It exits nonzero and prints the path with expected and actual SHA

Scenario: Demo runbook lists order fallback and Toutiao steps
  Test:
    Filter: demo_baseline_seal
  Given The runbook is written
  When It is checked against the final demo list
  Then Every demo app appears in order each has a skip fallback and the Toutiao and BoatAttack steps are present
