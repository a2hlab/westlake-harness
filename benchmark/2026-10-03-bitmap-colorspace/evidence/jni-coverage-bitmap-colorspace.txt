STUBS (hwui_register_stubs.cpp, gap 9b): only register_android_graphics_BitmapRegionDecoder,
  YuvToJpegEncoder, (and a few others) return JNI_OK WITHOUT registering methods. The MAIN
  register_android_graphics_Bitmap is NOT stubbed -- the live nativeComputeColorSpace strings prove it.

CONCLUSION (corrects cc-t3's "nativeComputeColorSpace has no ColorSpace" guess at the registration level):
  JNI coverage is COMPLETE. nativeComputeColorSpace is registered and genuine. It returns null BY DESIGN
  when the backing SkBitmap has no SkColorSpace:
    Bitmap.cpp:942-949  Bitmap_computeColorSpace: colorSpace=info().colorSpace(); if(colorSpace==nullptr) return nullptr;
  So the null is a GENUINE "source SkBitmap has info().colorSpace()==nullptr", NOT a missing/stubbed native.

INTERNAL INCONSISTENCY (the fix lever):
  Bitmap.cpp:925-930  Bitmap_isSRGB: `return colorSpace == nullptr || colorSpace->isSRGB();`
  i.e. isSRGB ALREADY treats a null colorspace as sRGB, while computeColorSpace returns null. Making
  computeColorSpace fall back to sRGB for a non-ALPHA_8 null-colorspace bitmap aligns the two.
