# Dynamic correlation backbone: U10.1T8 stage-A window5 first fatals (benchmark/2026-10-02-candidate-first-fatal-clusters, 27 clusters)
# mapped to CAUSE LAYER, to attribute which runtime STUBS actually block a key.
# Method: a stub is "LIVE" iff OH_RegHook shows its class.method resolving to liboh_android_runtime.so and NOT overridden
# by a later libhwui/bridge registration (ART: last RegisterNatives wins). A stub "blocks" a key iff that key's FIRST
# fatal traces to it. Silent stubs that return null leave no per-call log, so "reached" is attributed via the first-fatal
# stack (DFX backtrace / Java exception), not a generic marker (the generic UNSUPPORTED/stub markers are OH system noise,
# thousands/key, not our stub calls -- see note).

## Net dynamic result
Of all the deliberate runtime stubs, exactly ONE is a confirmed first-fatal cause in stage-A: Surface.nativeLockCanvas
(+ its pair nativeUnlockCanvasAndPost) -> fd-plus (1 key). Every other first fatal is a jar / native-lib / namespace /
policy / libhwui / app issue, NOT a runtime stub. So almost all "return null/0" stubs are benign on this corpus
(their assumption "no path strict-requires this" HOLDS here); the stub census below quantifies blocked-key count per stub.

## Marker-sweep note (why "reached" is not from generic markers)
Grepping 56 stage-A hilogs for UNSUPPORTED/stub returns thousands of hits per key -- OH system/RegHook noise, not our
stub calls. The specific markers (U12-MEDIA-UNSUPPORTED, FEATURE_*UNSUPPORTED) are 0. So silent stubs leave no per-call
log; "reached + first-fatal" is attributed from the first-fatal stack only.
