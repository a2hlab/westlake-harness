No board touched by this lane; evidence = existing 5cd run + 61b historical + cc-wiki live.**

## FALSIFIED mechanism (recorded so we don't revisit it)
I argued: the adapter hands the app the raw host dataDir `/data/app/el2/100/base/<pkg>`, which the enforced sandbox doesn't expose in-child → path-nonexistence → CANTOPEN. **Counter-evidence (cc-wiki, `westlake-harness-wiki/benchmark/2026-10-10-u13-autostart/evidence/61b-cantopen/expA-todolist-live-proc.txt`):** for a live app (privacyfriendlytodolist pid 11633), `/proc/<pid>/root/data` is the whole userdata mount (mountinfo `979 / /data`), and `/data/app/el2/100/base/<pkg>/databases` IS visible, owner = running uid 20010828, label normal_hap/appdat. So the raw path exists and is reachable in the child. The adapter does override dataDir to the raw path (studytracker hilog L36637 `[B43-BIND] dataDir overridden: /data/app/el2/100/base/com.edward.studytracker`), but that path is present — so dataDir-vs-sandbox-path is NOT the fault.

## What the failure actually is (constraints from all three sources)
- SELinux-mode-sensitive: cc-wiki's `setenforce 0` window showed **no CANTOPEN** (a screenshot artifact is being re-verified in a 3rd window).
- **avc-free**: no `avc:`/`audit`/`ioctlcmd`/`capability` line anywhere in the studytracker hilog; outer confirms no file-class `dontaudit` for normal_hap/hap_domain and `appdat` is all-perms `allow`. (The only "denied" lines are BMS IPC `GET_BUNDLE_INFO_PRIVILEGED`, unrelated; plus the benign `[ROUTE-A] child diagnostic fd errno=13`.)
- Trigger is today's reboot/v2-autostart state: pre-v2 the `appdata-sandbox.json` was mis-labeled so appspawn-x never enforced the sandbox; v2 relabel (→`system_etc_file`) turned enforcement on. libresudoku `-shm` last written 2026-10-10 00:22 (pre-reboot, i.e. it could write before enforcement). 61b now reproduces with DB files present (10-01/10-03), **dir/DB owner = BMS uid**, label appdat, no avc.

A clean "setenforce 0 fixes it, but no avc" almost always means a **dontaudit'd** denial (suppressed from audit) — on a class the outer did NOT rule out (file class was ruled out; capability / xperm / other classes were not).

## Candidate mechanisms (SELinux-mode-sensitive AND avc-free), ranked with hilog evidence
1. **`dac_override` capability, dontaudit'd (STRONGEST).** cc-wiki: on 61b the el2 DB/dir is owned by the **BMS uid**, but the app runs as the **per-app uid** (studytracker 20011117). Opening/creating under a dir+files owned by another uid requires `CAP_DAC_OVERRIDE` (or `dac_read_search`); SELinux gates it via the `capability` class, and capability denials are **routinely dontaudit'd** → no avc; `setenforce 0` grants it → open succeeds. Fits every constraint: mode-sensitive, avc-free, path-visible-but-wrong-owner, cluster-wide (ownership set at install/prep, not per-app). Open question: cc-wiki's todolist expA showed dir owner = *running* uid 20010828 — so ownership is **inconsistent** across apps; must confirm owner-uid-vs-runtime-uid for each *crashing* app. Evidence to pull on-board: `sesearch -A -s normal_hap -t normal_hap -c capability -p dac_override,dac_read_search` and any matching `dontaudit`; `stat -c '%u' <db>` vs runtime uid.
2. **F2FS ioctl xperm (`allowxperm`), dontaudit'd.** SQLite open/create on F2FS issues `fcntl`/`ioctl` (e.g. atomic-write / `F2FS_IOC_*`); enforcing gates specific `ioctlcmd` via `allowxperm`; if the needed cmd is outside the whitelist and the xperm denial is dontaudit'd → no avc; `setenforce 0` allows it. Evidence: `libcore.io.Linux::ioctl*`/`fsync`/`posix_fallocate` hooks are registered for this app (L33896–33949); no `ioctlcmd` avc seen (consistent with dontaudit). On-board: `sesearch --allowxperm -s normal_hap -t appdat` and strace/ftrace the failing ioctl.
3. **XPM / code-sign (separate LSM, enforce-gated, logs `CODE_SIGN` not avc).** Evidence: `CODE_SIGN: [XpmIoctl]:Ioctl cmd 40087803 failed: Bad address (ignore)` at spawn (L33141). XPM enforces code integrity and is tied to the enforce toggle, logging to CODE_SIGN not avc. WEAK for a DB open: it fires at spawn (code pages), is marked "ignore", and DB files are not executable. Lower.
4. **Security-component subsystem (`SecCompEnhanceAdapter`).** Evidence: `libsecurity_component_client_enhance.z.so` load failed errno 2, `SecCompEnhanceAdapter [InitEnhanceHandler] init ... failed` (L33145–33148). If a security component is required under enforcement its absence could block an operation — but a missing lib (errno 2) is enforce-independent, so this is unlikely the mode-sensitive lever. Lower.
5. **`getenforce` / `/sys/fs/selinux/enforce` behavioral branch in runtime/adapter/appspawn-x.** No `getenforce` read by the app in its hilog; if such a branch exists it is in a system service (appspawn-x preload). Low from the app log; needs a system-side check.

## Minimal board experiments to settle it (cc-wiki is on /proc/<pid>/root + setenforce; suggest next)
1. **Confirm the setenforce 0 result (3rd window)** on a known-crashing app (studytracker/listmaker): enforcing → CANTOPEN, permissive → opens, with `dmesg`/`hilog` captured both ways. If permissive clears it with still no avc → dontaudit'd denial confirmed.
2. **Ownership probe (decisive for #1):** `stat -c '%u:%g %a' /data/app/el2/100/base/<pkg> /data/app/el2/100/base/<pkg>/databases /data/app/el2/100/base/<pkg>/databases/<db>` vs the app's runtime uid (from `ps`/hilog). If owner ≠ runtime uid → `dac_override` path.
3. **Capability/xperm policy query:** `sesearch -A -s normal_hap -c capability -p dac_override,dac_read_search`; `sesearch --dontaudit -s normal_hap`; `sesearch --allowxperm -s normal_hap -t appdat`. A dontaudit on capability/ioctlcmd that `setenforce 0` bypasses pins the class.
4. **As-uid probe in permissive vs enforcing:** as the app uid in `u:r:normal_hap:s0`, `sqlite3 <db> .tables` (or touch+open) in each mode; compare errno.

## Fix direction (pending the pinned class)
- If `dac_override`/ownership: make the el2 DB/dir owner the **per-app runtime uid** (fix the install/`sandbox-command.sh` chown so it targets the runtime uid, and relabel/re-chown already-created DBs) so no cross-uid access is needed — no policy relaxation. (Recovery on a broken board: `chown -R <runtime-uid> /data/app/el2/100/base/<pkg>` — derived data, safe.)
- If `allowxperm`/ioctl: add the specific `ioctlcmd` to the normal_hap↔appdat `allowxperm` whitelist.
- General: the frozen 128 baseline was captured with the sandbox silently off (pre-v2 label), so a full-128 re-baseline under real enforcement is warranted once fixed.
