# Narrowed malloc-hook refuse list — per-lib hook-target verification (#48)
date: 2026-09-26

## Why narrow
The broad refuse (17 libs = every bytehook/shadowhook user that referenced a
malloc-family name) killed the warm SIG11 but also refused libhotfix-opt, a
FUNCTIONAL lib that hooks no allocator; its class init then failed and the app
_exit(1)ed ~61 s. A lib can reference "malloc"/"free" for two different reasons:
  (a) a UND import  -> the lib CALLS malloc (harmless)
  (b) a .rodata string constant passed to a hook-install call -> the lib HOOKS
      malloc (this is what corrupts musl mallocng)
`strings | grep malloc` conflates the two. The correct criterion is (b).

## Per-lib verification
For each bytehook/shadowhook user: does .rodata contain a malloc-family string
(the hook target) AND does the lib import a hook-install function
(bytehook_hook_* / shadowhook_hook_sym_*)? Hook-target profile from .rodata
function-name strings.

## Correction to the "functional" assumption
jato/monitorcollector/sysoptimizer were assumed functional/non-malloc, but the
disassembly shows they DO hook the malloc/free family (jato: free×4 + I/O;
monitorcollector: malloc×2; sysoptimizer: free×1), and jato/monitorcollector were
mapped on the warm crash run. By the hook-target criterion they are refused. They
are I/O/perf/APM diagnostics, not on the read path, so refusing them should not
break reading — but if the board shows a NEW _exit(1) from one (unguarded loader,
like hotfix), drop that one; if SIG11 then returns, that lib was the corruptor and
needs a no-op engine stub instead of a refuse. libnpth stays out of the list
(fresh-proven safe, unsafe to refuse).
