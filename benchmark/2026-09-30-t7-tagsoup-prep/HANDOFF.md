## The fix (done)
`bms/src/adapter/framework/mainline-stubs/java/org/ccil/cowan/tagsoup/Parser.java` — added
`setProperty(String,Object)` + `getProperty(String)` + the four upstream TagSoup property-name constants
(`lexical-handler`, `scanner`, `schema`, `auto-detector`) and their backing fields. Recognized names
store/return the value; an unknown name throws `SAXNotRecognizedException` (upstream semantics). Fields
are `Object` because this stub does not parse and the Scanner/Schema/AutoDetector types are not stubbed.

## IMPORTANT finding for the outer loop
The stub `Parser` was **otherwise EMPTY** (only a no-arg constructor; auto-generated by
`scan_bcp_class_gap.py`). So `setProperty` passing only exposes the NEXT missing `Parser` method
(`setContentHandler`/`setFeature`/`parse`/...). **wikipedia's actual HTML rendering needs the full
upstream TagSoup ported into the mainline-stubs jar**: `Parser` + `Scanner`/`HTMLScanner` +
`Schema`/`HTMLSchema` + `HTMLModels` + `AutoDetector` + `Element`/`ElementType`/`AttributesImpl`
(+ `PYXWriter` for CLI, not needed). `HTMLSchema` is already present as a stub next to `Parser`.
This setProperty is the first hand-routed method (§15.1 第 3 条); the full port is the #91 follow-on and
should be scoped as its own task if wikipedia's rendered content (not just "past setProperty") is the
goal. The other four J4-boot-api gaps (getNetworkSpecifier / EXTERNAL_CONTENT_URI / NetworkInfo.getState
/ getLinkUpstreamBandwidthKbps) are the same shape: single missing methods/fields on boot-stub classes.
