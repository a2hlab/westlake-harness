## Which of our methods returns null -- android_graphics_compat_shim.cpp:79 (ImageDecoder.nGetColorSpace stub)
android_graphics_compat_shim.cpp:72-80 (registered for android.graphics.ImageDecoder, kImageDecoderMethods:113):
  // G2.4 (2026-04-30): nGetColorSpace's libhwui impl caches gColorSpace jfieldID via GetStaticFieldID at register
  // time. When that fails (class layout mismatch on our framework.jar), the cached fid stays null; subsequent
  // GetStaticObjectField(env, ..., null) trips CheckJNI abort.
  // Override: return null so caller's getColorSpace() returns null.  No Android UI path I know of strict-requires
  // non-null ColorSpace; sRGB is assumed when null.
  jobject ID_nGetColorSpace(JNIEnv*, jclass, jlong) { return nullptr; }
=> fd-musicplayer REFUTES that stated assumption: Bitmap.createBitmap(source,...) DOES strict-require a non-null
   color space (throws otherwise). A bitmap decoded via ImageDecoder gets its color space from nGetColorSpace; our
   stub returns null -> the decoded bitmap has mColorSpace=null -> createScaledBitmap throws.

## Why the null workaround may no longer be needed
The G2.4 workaround returned null to dodge a ColorSpace-class fid==null CheckJNI abort (ColorSpace class not loaded
when ImageDecoder's register cached the static fieldID). That ordering was since fixed: AndroidRuntime.cpp:306 now
registers ColorSpace BEFORE ImageDecoder/Bitmap/HardwareBufferRenderer ("must register BEFORE ImageDecoder/Bitmap...
ImageDecoder's register_X caches a jfieldID for ColorSpace static field (e.g. SRGB)"). So returning a real sRGB
ColorSpace from nGetColorSpace should no longer hit the original abort.
