# U13 device-native boot recovery port — static plan only

## Evidence first: what must not be copied

**A boot mount worker is not an Android spawn parent.** The 2026-09-28 Toutiao
script executed under `u:r:su:s0`, but its directly spawned Android child failed
`PR_SET_KEEPCAPS(0)` with EPERM. Merely making a script run, switching to `sh:s0`
(which did not run), or clearing securebits (also EPERM) did not solve recovery.
The BoatAttack donor instead prepares mounts and asks **init** to start the
existing AppSpawnX service; it records `activity_start=DEFERRED_TO_USER` and
`pid=NONE`. This is the architectural seam to reuse, not the donor binaries.

The actual 61b U13 recovery already succeeded through the host executor:
**56 visible baseline mount rows, 319 expected paths / 321 assertions**, runtime
`452447a4a0ba` over 124 paths and boot `ee927db88a67` over 36 paths. The restored
host is `2a87118e7e8e62fb73ef71a436517cda406c308668753a478cf52331e996072e`.
This is evidence for replaying the recorded bytes, **not** evidence that a new
init hook or its SELinux/capability profile works on 61b.

`autostart-evidence.json` pins the unchanged original journal (`f2471873…`),
current source files and all 56 ordered rows/source SHA. It is generated by the
existing **pure** `u7_executor.baseline_replay_plan`, without constructing a
DeviceIO or invoking any subprocess/transport. No startup cfg, native byte,
mount, permission, service, application or gate table is changed here.

## Recommended service split

Port the **shape**, keeping existing signed U13 native/JAR/boot bytes unchanged:

1. One condition-started, noncritical **mount worker** after `/data` and the
   relevant EL1 package directories are available. The donor uses
   `bootevent.boot.completed=true`; repeat that condition in the worker itself.
   A proposed dedicated init cfg is `/system/etc/init/00_westlake_u13_recover.cfg`
   and script `/system/etc/westlake-u13-recover.sh`, with persistent receipts and
   immutable payload tables under `/data/westlake-demo/u13/`. These are proposed
   names only, not installed artifacts. `uid=root`, `gid=[root,system]`, `once=1`,
   `sandbox=0`, condition start; the donor's su service can be the mount-worker
   reference. Capabilities needed for the proposed operations are
   DAC_OVERRIDE/CHOWN/FOWNER/SYS_ADMIN; do not copy SYS_PTRACE or CAP_SETPCAP merely
   because another script has them. Exact minimal caps/domain remain admission
   work, not established by this paper.
2. Existing init-owned **appspawn-x** service remains the only Android parent.
   After all mounts, approved private overlays and full byte checks, the worker
   requests `begetctl start_service appspawn-x`. It never directly executes
   appspawn-x, `source_app_namespace`, an Android launcher or a watchdog that
   automatically launches an app. Preserve the service's socket and accepted
   environment/security profile; do not invent a second parent service.
3. Publish a new boot-bound receipt, atomically, only after one stable parent
   (UID0, PPID1, exact U13 executable SHA) and the owned listening socket pass.
   A proposed `sys.westlake.demo.u13.ready` parameter is advisory: its permissions
   and init trigger must be checked. The receipt's current boot ID + table SHA,
   file/view hashes and error state are authoritative, not an old `READY` file.
   `READY` means **runtime prepared, applications stopped**, not screenshot-lit.

Do not install the donor base cfg and Boat cfg together: both define the same
PR03 service. Read the actual board init files first; back up and explicitly
supersede any conflicting old PR03/Boat recovery job before admitting one owner.
Do not leave two boot workers replaying different generations in parallel.

**Important non-portable donor behavior:** the PR03 hook invokes `setenforce 0`,
changes persistent runtime/prefork parameters, chmods Mali, broadly relabels
directories, and makes a boot.art link. The Boat hook updates BMS label databases
and force-stops its UID. None is automatically approved for this port. Preserve
the sealed enforcement mode, existing U13 parameters, labels, installer, DB and
devices; require narrowly justified changes if execution would otherwise fail.
If the worker/helpers cannot run under the accepted enforcement state, stop for
outer review rather than make the whole board permissive.

## Exactly where the 56 mounts replay

Compile the **old transaction's visible baseline**, not its U14 candidate
`changes`, into a device-local fixed table. Use the resolver's sources and SHA,
not filenames guessed from a bundle. The old journal is immutable; per-boot
operation receipts must be new. Python, Mac/VM, native tickets and board-lock
transport stay on the host side during admission. A future minimal device worker
consumes a pinned table; it must not run the host executor verbatim.

**Ticket freshness is separate from byte identity.** The board's 2026-10-09
22:07:39 recovery entry reports a pre-lock refusal, `native inputs changed
across dispatch`, for an old U14-window6 ticket. The 22:13:25 entry reports the
fresh approved U13 ticket passing with the same signed 319 bytes. Admission and
manual recovery therefore need a freshly checked current policy binding; never
disable the check, mutate the historical journal, or treat its old native ticket
as a permanent boot authorization. A device-local fixed table requires its own
reviewed, sealed authorization and explicit revocation/disable mechanism.

This order is the original resolver's stable depth sort (directory before its
direct child file), not “mount all .so then jars”. All **56 rows finish before
AppSpawnX is started**, including the five private control-library mounts.
`autostart-evidence.json.layers` lists every target, exact original persistent
source, direct file SHA, old stack and journal pointer. The original top layer
only is replayed, not every buried historical generation.

The resolver expects **313 unique source files** for 319 target paths (alias
sharing): **306 `/data` sources + seven untouched `/system` members**. The seven
are both aliases of installs/BMS/apk_installer and chipset libc++. They are
verified, not remounted/replaced; preserve 61b's signed installer `51e1b525`.
`/data/local/tmp/u7-…/fN` is reboot-persistent storage, not a disposable host temp
folder; do not delete old sources. Before boot deployment, archive/copy these
exact bytes into a durable root, verify every SHA, and bind the new table/source
mapping explicitly. Relocation changes provenance/table SHA, not payload bytes.

### Per-boot sequence

- Check DISABLED, same-boot current receipt/idempotence, readiness of `/data` and
  package roots, all source/stock SHA and target types. Preserve init's AppSpawnX
  listener and require **no live parent/children**. On a clean no-daemon boot do
  **not** call stop_service: the donor documents that it destroys the listener.
- Verify current mount stacks are empty or the exact admitted partial prefix.
  Unexpected owners fail closed; no broad unmount sweep. Append a write-ahead
  receipt for each row, bind, then verify exact top source/device and unchanged
  prior stack. Repeated invocation must verify the existing owned result rather
  than add another layer.
- After the 56 baseline binds, apply the narrow placeholder rule before starting
  anything: only old `plan.additions` targets, parent/children stopped, **no exact
  mount**, absent or SHA EMPTY. Here the sole target is
  `/system/android/lib64/libicu74compat.so`. Mounted/nonempty/undeclared paths
  are refusal, never deletion. Then all 319 expected bytes + declared absence
  must match. This avoids the observed 124→125 glob drift (`204ab50509d1`).
- If the final demo admits BoatAttack, layer **its approved new JAR + three
  private files after baseline and before the parent**, not the donor's ten
  shared native replacements. Treat these as separate declared owned layers;
  56 baseline rows are not the final demo total. Recheck the **final seal**, whose
  runtime fingerprint can differ after the approved JAR. Route B's persistent
  ttbundle/HAP files are checked separately; its private mount namespace is not
  a replacement of U13 `/system` and no feed/watchdog is auto-started here.
- Start AppSpawnX through init, verify executable/parent root view and socket
  `0:6005`, `0660`, `u:object_r:appspawn_socket:s0`, LISTEN, stable unique parent.
  Write current-boot MANUAL receipt. Do **not** call `DeviceIO.verify` or
  activation_smoke in the boot hook: those intentionally launch control apps.
  Full parent/child 321-assertion and HW/ZZ screenshot checks remain separately
  authorized admission tests, after the hook has left all applications stopped.

## Avoiding the su/KEEP_CAPS wall — and remaining uncertainties

Use su only for filesystem preparation if its admitted profile is needed. A
`begetctl` request starts the **existing service as init's child**; the Android
parent is not descended from the su worker and does not inherit that worker's
locked securebits. Its children continue through the accepted stock appspawn
privilege flow. This is why the donor's PPID1 check and existing executor's
service start are relevant. Do not add the old proposed “EPERM + GET_KEEPCAPS=0
means success” native patch: it was not implemented in the September report,
would change signed bytes, and is not required by the service split.

This is a **source-based design inference**, not a new privilege-flow test.
Before enabling, capture actual 61b init cfg SHA/fields, init/worker/parent/child
contexts and `Cap*`/NoNewPrivs status; bind evidence of securebits/KEEP_CAPS only
through an approved diagnostic if needed. The 319-path U13 identity does not
include appspawn_x.cfg. Master has both a boot-start source variant and ondemand
variants; do not substitute a source copy for the deployed cfg. Existing
ondemand config cannot casually combine `critical`, `disabled`, or `start-mode`.

The ondemand listener can receive an early AMS request before a boot-completed
worker finishes. Keep the donor's no-parent guard at entry and every bind; if it
fires, do not kill/retry/remount underneath a live tree. Admission must demonstrate
that the selected boot ordering beats this race. If not, a separately reviewed
init/listener startup ordering gate is needed; this plan does not claim that
an untested `ondemand + condition` combination solves it. Likewise, an enforcing
worker/helper denial is an unresolved init-policy requirement, not a reason to
broaden global SELinux or clear securebits.

Route B is a distinct parent architecture. Restoring its files here does not
prove its direct `source_app_namespace` launch has escaped the September su
inheritance issue; its eventual **manual** SAFE broker/launch path needs its own
current-boot evidence. No automatic app launch is part of this U13 plan.

## Rollback and enablement gates

1. Before install (future authorized spare-board window), archive exact original
   cfg/script, absent-file markers, file metadata and all baseline/overlay SHA.
   Verify ROM/serial; donor hardcoded whitelist/generation must not be reused.
   Install only approved hook/cfg/table files, finish with root read-only, and
   start **disabled**. Record config/script/table hashes separately in the seal
   support-file inventory; do not silently add them to the production 124-path
   runtime fingerprint or claim the short hash covers init configuration.
2. First validate on an explicitly authorized spare board's own signed variant,
   not 61b as an unannounced experiment. Known answers: disabled; missing/drifted
   source; foreign mount; partial replay; mounted/nonempty placeholder; stale
   READY boot ID; early parent; BMS/private missing; no new app PID. Then an
   authorized reboot verifies one parent, all effective identities, no auto app
   launch, unchanged enforcement/parameters, and manually launched HW/ZZ views.
3. Enable on 61b only after outer/user authorize the demo-board startup change.
   Stop-on-failure, bounded boot-ready deadline <=600 s, atomic current-boot
   FAILED receipt and no restart loop. OS boot itself must not be blocked; do not
   publish runtime-ready on error. A partial mount failure keeps Android parent
   stopped and receipts/sources intact for outer review.
4. To revert integration, mark DISABLED first and stop **only this once worker**,
   restore the backed-up cfg/script/parameter policy (including absence), then
   verify root read-only. Disabling a hook does not undo active U13 mounts.
   Never unmount shared libraries under a live parent; shared unmount is deferred
   until a reviewed stop/reboot. Any live teardown uses cold-stop verified child
   UID/PPID ownership then begetctl, **never kill -9 the main parent**.
5. At a permitted stopped-parent maintenance point, undo only mount operations
   recorded as owned by this new hook in reverse dependency order; unexpected
   top owner refuses rollback. Delete only owned absent-origin EMPTY placeholders
   after their binds are removed. Never remove raw payload sources or unrelated
   init/system files. Alternatively reboot disabled and let cx-t0 run the pinned
   manual newboot replay to restore U13, with a new journal, 319/321 identity,
   4524/ee927 fingerprints, HW/ZZ smoke and outer screenshot signoff before UNLOCK.
   A disabled reboot alone is **not** “restored U13”.

**Decision:** conditionally feasible with an init-owned parent and the exact
recorded mount table; **no candidate, install or boot validation yet**. Next
approval gates are actual deployed init cfg/domain, sealed enforcement policy,
ordering race and final demo-overlay identities. No U13 binary rebuild or broad
BoatAttack shared-runtime transplant is proposed.
