WHY IT NEVER REACHED THE weatherView ASSIGNMENT (the mechanism, from the timeline):
  34.809  AndroidEventLog performCreate org.breezyweather.ui.main.MainActivity     (onCreate RAN)
  34.811  AMS [UALM577] Ability ... start to foreground ; [ABR370] ForegroundLifecycle MainActivity
  34.812  [stderr] J_invokeStaticMain_main_threw ... weatherView ... (the crash, via b14.run Handler callback)
  34.812  OH_LifecycleAdapter: state=INITIAL->FOREGROUND -> RESUMED activityToken=...@ced31ae
  34.812  OH_LifecycleAdapter: dispatchByActivityToken POSTED to main Looper: RESUMED
  - weatherView is a lateinit in HomeFragment, assigned in the fragment's onCreateView/onViewCreated.
  - onCreateView runs when the host advances to onStart/onResume (FragmentManager executePendingTransactions).
  - route-A's OH_LifecycleAdapter dispatches FOREGROUND->RESUMED (i.e. onStart/onResume) as a SEPARATE POSTED
    Looper message AFTER onCreate returns. The app posted a runnable (b14) DURING onCreate; that runnable was
    already queued ahead of the posted RESUMED, so it ran FIRST -> HomeFragment.v() read weatherView before
    onCreateView had assigned it -> UninitializedPropertyAccessException.
  - On stock Android handleLaunchActivity runs onCreate->onStart->onResume SYNCHRONOUSLY in ONE transaction, so
    the fragment's onCreateView executes (weatherView assigned) before the Looper processes b14 -> no crash.
    (No onCreateView / addView / handleResumeActivity / setContentView marker appears before the crash here.)

CLUSTER: not CoroutineStart. New own cluster "async-lifecycle-ordering": an app onCreate-posted main-thread
callback runs before the fragment onCreateView that initializes a lateinit view, because the adapter advances
onStart/onResume via a posted Looper message instead of synchronously inside the launch transaction.

MINIMAL FIX (ours — OH_LifecycleAdapter / AppSchedulerBridge): drive onStart/onResume (and thus
executePendingTransactions -> Fragment.onCreateView) SYNCHRONOUSLY within the create/launch dispatch, as AOSP's
handleLaunchActivity does; at minimum run the pending fragment transactions before returning from the create
dispatch so fragment views exist before any onCreate-posted callback runs.

PREDICTED KEYS MOVED: 1 (fd-breezyweather past the lateinit, to its next wall; lit not guaranteed). The lever
is shared, so other Fragment apps that post onCreate work touching fragment views may also benefit — not
counted here. (No standalone app-specific small fix; the fix is in our lifecycle dispatch.)
