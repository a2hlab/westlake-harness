## (1) U12 private-zlib scope -- the outer's question
U11ZlibRoot(search, permitted) (zlib-route.h) returns "/system/android/lib64/westlake_native" for EXACTLY TWO packages:
  { "im.vector.app", "com.emn8.mobilem8.nativeapp.bk" }   (Element and burgerking)
and NULL otherwise. So the private zlib is SCOPED to {Element, burgerking} -- not universal, not burgerking-only.
**Element (im.vector.app) is already enrolled.** For Element U11ZlibRoot prepends westlake_native to the app search/
permitted paths, where westlake_native/libz.so (50b9ab6a) provides crc32 for librealm-jni's NEEDED libz.so.
=> The 02:53 report is U10.1T8 (which PREDATES the U11/U12 private zlib). **U13 (host 2a87118e) already fixes Element's
   libz** via the private-zlib search prefix. No public-lib change is needed for Element's libz.

## (2) Avoid two libz in one process -- the outer's constraint
Do NOT add libz.so to the public-lib inherit. The only libz-needing apps today (Element, burgerking) get libz from the
private-zlib search prefix (westlake_native, LOCAL_NS_PREFERED -> preferred, single copy in the app ns). If libz.so were
ALSO in the bridge inherit, the platform libz (from default) could load as a SECOND copy -> two libz in one process.
=> the patch's public set EXCLUDES libz.so: "libicui18n.so:libicuuc.so:libGLESv2.so:libGLESv3.so:libvulkan.so:libjnigraphics.so".
   (The GL/ICU libs are safe to add even though some private apps also inherit libGLESv3 via system_owner: both edges
   point at the same DEFAULT-ns copy, so the linker dedupes -> one instance. Only libz has a separate provider, hence
   the exclusion.) If a FUTURE non-enrolled app needs libz, either enroll it in U11ZlibRoot OR add libz to the inherit
   AND drop its private-zlib -- never both.
