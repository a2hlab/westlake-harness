  log fires for EVERY launch, so ordinary=false is the discriminator).
Source B (what theme the deployed JAR resolves): [B8-ALIASTHEME] "<targetActivity> theme re-resolved X -> Y"
  (X != Y = the fix will change the resolved theme) or "theme unchanged (Y)" (X == Y = fix is a no-op).

NOTE ON HOW THE FIX WORKS (from benchmark/2026-10-03-u15-fdapi-theme):
  AOSP: an <activity-alias> with no android:theme inherits the TARGET activity's theme.
  route-A today: AppSchedulerBridge:793 `if (ai.theme==0 && appInfo!=null) ai.theme=appInfo.theme` falls a
  themeless alias back to the APPLICATION theme (X). The deployed U13 JAR already LOGS the target theme Y via
  [B8-ALIASTHEME] but does NOT apply it to the ClientRecord launch.theme. cc-t3's U15 JAR v1 makes it APPLY Y
  (AOSP alias-inherits-target). So "X -> Y" = the alias launch's activity theme moves from the app-theme
  fallback (X) to the target activity's own declared theme (Y).

KEY FINDING: every target theme Y that differs from X is a SPLASH theme
  (AppTheme.Splash / SplashTheme / MwmTheme.Splash / SplashScreenThemeBase / Theme.Vector.Launcher).
  Reason: these apps declare the Android-12 SplashScreen pattern on the launched component (the launcher
  component carries a splash theme; the app calls installSplashScreen()/setTheme() after first frame to swap
  to the real UI theme). So applying Y governs the PRE-CONTENT (splash) window only; the steady-state t20 UI
  is the app's real theme, reached after the splash is dismissed.

------------------------------------------------------------------------------------------------------------

(section A minus fd-api). cc-t3's dispatch says 8. The most likely +1 is fd-fennec_fdroid (Firefox):
its first-fatal is fatal-BEFORE-bind (libmozglue.so UnsatisfiedLinkError), so the alias theme is never

  { wikipedia, fd-notes, fd-calendar, fd-filemanager, fd-gallery, fd-musicplayer, fd-organicmaps,

the per-key verdict is identical either way (fennec is dead-before-window, theme not observable).
