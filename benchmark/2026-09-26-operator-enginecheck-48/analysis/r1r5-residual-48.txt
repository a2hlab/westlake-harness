## r5 = sigaction Bionic-vs-musl ABI overrun in ANOTHER lib = libmonitorcollector-lib
- Fault: musl sigaction (0x1117d0) at +0x184 (0x111954) `stp q0,q1,[x19,#96]` — x19 = the
  caller's `old`/oldact buffer; musl copies the FULL 152-byte struct sigaction (sa_mask =
  sigset_t 128B/1024 sig) into it. `cbz x19,...` at 0x111948 is NOT taken => old is NON-NULL.
- npth (the prior sigaction offender) is now the HOLLOW stub (no sigaction). Of the r5-loaded
  libs, the ONLY one importing sigaction@LIBC is **libmonitorcollector-lib** (godzilla-memsponge/
  jato/npth_bt/npth_dl do not import it). monitorcollector's hooks were neutered by f3918bdc but
  its sigaction CALLS were untouched -> it passes a Bionic-sized `old` (~40B: sa_mask=8B/64 sig)
  to musl, which writes 152B -> ~112B overrun -> when the buffer is <152B from a page edge, the
  tail hits an unmapped/RO page -> SIGSEGV on the platform-handle (crash-handler) thread.
- This is the SAME class as npth's r5 (I patched npth's 14 non-null-old sites); monitorcollector
  is a second offender, and MORE libs may do it (any Bionic-built lib installing signal handlers
  with a saved old).
- FIX RECOMMENDATION = UNIVERSAL musl-side sigaction shim (>> per-lib whack-a-mole). westlake
  ALREADY intercepts sigaction (see r1/r5 stderr `[WESTLAKE-WEBVIEW-SIGNAL] sigaction #N ...`).
  Extend that interceptor so that for EVERY caller with a non-null oldact: call the real
  sigaction into an INTERNAL 152-byte musl-layout `old` buffer, then copy back ONLY the
  Bionic-struct-sized prefix (sa_handler @0, sa_mask[0..8], sa_flags, sa_restorer) into the
  caller's buffer -> the caller's small buffer is never overrun; it still gets the fields it
  reads. One shim change covers monitorcollector + npth + every future offender, arch-clean, no
  per-lib binary patching. (Per-lib alt: patch monitorcollector's sigaction calls like npth's
  7639af00 — needs the arm64 monitorcollector baseline, and only fixes this one lib.)

## r1 CONFIRMED via arm64 libsscronet.so disasm (sha 38f0dd42…, handoff) — NOT a hook, cronet C++ lifecycle
Fault 0x28a21c is a C++ VIRTUAL CALL in cronet's TTNet detection code:
  28a20c: ldr x0,[x20,#0x568]   ; x0 = detector object ptr (field 0x568 of x20)
  28a218: ldr x8,[x0]           ; x8 = vtable = *x0
  28a21c: ldr x8,[x8,#0x28]     ; CRASH: x8(vtable)==0 -> read 0x28  (si_addr=0x28)
  28a220: blr x8                ; virtual dispatch
x0 is a VALID pointer (else 0x28a218 ldr x8,[x0] would fault at 0, not reach 0x28a21c); [x0]==0
means the detector object's VTABLE is null -> object allocated but NOT constructed (or destroyed).
The sibling path just above (0x28a1cc: ldr x8,[x20,#0x40]; ldr x0,[x8,#0x28]; cbz x0, skip; ...)
DOES null-guard its virtual call; the crashing [x20+0x568] path does NOT. The detectors are
cronet/TTNet's own C++ objects (rodata: ttnet_raw_detect / stress / exception / feedback /
polling_detect). A monitor hook does NOT construct cronet C++ objects, and a MISSING hook would
leave a null object POINTER, not a valid object with a null vtable. => r1 is NOT a load-bearing
hook. It is a cronet/TTNet detector object lifecycle issue (read-before-construct or use-after-
destroy) on an unguarded virtual-call path, network/config-timing dependent (=> intermittent,
3/5 fine), UNMASKED now that the heap fix lets the app reach this network-detection path. The
engine hollow did not cause it (it removes inline hooks; it does not touch cronet C++ construction).

r1 FIX: NO pass-through engine (not a hook). A binary guard patch on sscronet is NOT clean: no
>=32B zero code-cave exists in .text (Chromium is densely packed; padding is nop/brk not zeros),
and an in-place vtable-null guard needs +1 instruction that does not fit the 6-slot window. So a
guard would need a fragile nop-padding detour in a 4MB functional network lib (moderate risk of
breaking networking). RECOMMEND instead: (c) root-cause why the TTNet detector at [x20+0x568] is
unconstructed on OH (likely settings/config-fetch timing — startup shows many connect errno=115
IPv6-unreachable, so a settings/detector-config load may not have completed when this network
event fires this path) — a cleaner, safer fix than patching cronet control flow; or (a) tolerate
(intermittent 3/5). If the outer loop still wants the guard, I can build the nop-padding detour
(cbz vtable -> skip the dispatch, mirroring the sibling guarded path) on the handoff sscronet,
flagged as moderate-risk, board-test-gated.

## r5 namespace judgment (the outer loop's key check) -> PER-LIB, not universal shim
DECISIVE evidence: r5 crashed INSIDE musl sigaction (0x1117d0). That means monitorcollector's
sigaction call resolved DIRECTLY to musl — westlake's existing sigaction interception
([WESTLAKE-WEBVIEW-SIGNAL]) did NOT reach it. So a "universal westlake sigaction shim" as
currently architected would also miss monitorcollector (same OH-musl namespace blind spot that
killed the LD_PRELOAD hook-API master-switch e692f8fd). Per the outer loop's rule (prefer
namespace-robust; don't ship a shim that can't intercept), r5 fix = PER-LIB, file-level patch of
libmonitorcollector-lib.so's sigaction calls (namespace-robust: the patched .so file is what
loads, regardless of namespace/SOURCE-NATIVE-LOAD), exactly like the npth sigaction neuter
(7639af00): for each `bl sigaction` site that passes a non-null old (x2 != xzr), replace with
`mov x0,#0` (fake success; musl then never writes the oversized old struct -> no OOB). Keep
old==NULL sites (musl doesn't write old). NEED the arm64 baseline libmonitorcollector-lib.so
(sha f3918bdc42b60a19edc3b80c4bd1c1cadc972eba286e5f1b1447505a6bff1793, per handoff hashes) — NOT
in the sscronet handoff. (A universal shim is only viable IF westlake can interpose sigaction as
a GLOBAL libc symbol like it does dlopen — needs the westlake bionic-shim architecture confirmed;
the r5 crash shows the current interception is not global. Until confirmed, per-lib is the safe
namespace-robust choice.)
