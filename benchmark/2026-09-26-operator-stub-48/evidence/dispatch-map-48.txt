## Why the Boolean values are TRUE, not false
- 0x04000004 (Lms/bd/c/f3;->run) is a spin-wait:
      Boolean r = (Boolean) a(0x04000004, ...);
      if (!r.booleanValue()) { Thread.sleep(500); goto retry; }   // loops on false
  Returning false would hang the thread in a 500 ms retry loop. TRUE breaks it.
- 0x04000001 (Lms/bd/c/p2;->d, reached from MSManagerUtils.init) unboxes the
  Boolean and records call timing, then returns the flag to its caller. This is
  the exact site that NPE'd under the null stub (board stub-r1/r2). TRUE = "ready/ok"
  is the non-blocking answer.
Integer results (0x08*) are 0 (neutral status code, e.g. z3$e enum default path).
Strings are "" and arrays empty: the app compares them against real signatures
(f3.run: a(0x01000001) equals g3.b().toUpperCase()) — "" won't match, so the
security action is skipped, which is the intended metasec-unavailable behaviour.
