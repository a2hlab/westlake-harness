# Exact libandroid geometry source closure

The two `libandroid.so` paths must not be conflated. The runtime root file is `c9969638`; `webview-t-lib/libandroid.so` is `76512d97`. Both are present on 5cd. T21 did not collect its geometry GOT slot: the current caller's winner remains unknown. Historical R10 selected the latter for geometry; file evidence alone does not establish T21 binding.

The exact 765 artifact is present in `$INPUTS/out-sp20/webview-shims/libandroid.so`, 39,976 bytes. Its original `artifacts.json` binds source `37cfbdcb` and the one-step C compile/link command to that full artifact hash. `original.c` is the exact 36,330-byte source, not the different native691 copy. See `provenance.json` for full hashes. There is no retained original C object: the recorded command directly compiles and links the translation unit. The original zero-byte `libandroid.log` is preserved as evidence of an empty log, not invented proof of a separate rc=0 receipt.

The unchanged source was compiled locally with the original OH sysroot/CRT/builtins and the available Mac LLVM compiler. Frozen check, driver expansion, dependencies and build all returned 0; raw argv/stdout/stderr/rc are indexed in `private-raw-index.json`. The new file is `8026205d`, 40,064 bytes, **not byte-identical** to 765. All 20 allocated code/data sections apart from the build-id note are byte-identical with identical section headers; NOBITS headers also match. Differences are compiler `.comment` bytes, the build-id and subsequent nonallocated file offsets. This demonstrates reproducible executable content under a recorded host-toolchain difference, not exact-file reproduction. No candidate was built or deployed.

## Narrow repair boundary

`original.c:679-692` stores the Android requested format keyed by the original wrapper and sends that same wrapper directly to `NativeWindowHandleOpt`. Geometry failure returns immediately; the format conversion is never applied. The exact source maps Android format 2 to OH format 11. An observed request of format 2 is therefore not evidence of the actual buffer format.

The minimum prospective repair is confined to this geometry entry for the admitted player: preserve the original wrapper for identity/format bookkeeping; use the already reviewed owner acquire/get-OH/release lifetime route; send only the resulting OH window to geometry and format operations; bind HandleOpt to the same actual provider instance selected by the owner Reference/Unreference slots. Reuse the T20 owner checks rather than raw-OH fallback or a new pointer registry. Preserve existing nonplayer behavior, original dimension arguments, format conversion and return-code propagation. A geometry success followed by a format failure must still return that failure. Failed unwrap must not pass the original pointer to OH. No width/height/format getter family change is proposed here.

The older owner `aanw_perform` (main `bridge-d4fa-source-snapshot/base/westlake/framework/window/jni/oh_anativewindow_shim.cpp:558-595`) already unwraps before OH geometry, but its format error is not propagated and its compile-time format branch differs. It is evidence for the object boundary, not a function to copy wholesale into this entry.

## What this does not establish

The T21 five successful CPU pairs and subsequent `Invalid GrBackendTexture` belong to startup splash video. Its NativeImage/SurfaceTexture chain is distinct from the logged main UI wrapper. Size 1200x2132 alone does not establish accidental main-window sharing or an illegal size. A geometry fix can remove the demonstrated wrapper-to-OH boundary error only if the actual call selects this path; it does not prove that the later backend texture import will succeed. Actual geometry winner, changed geometry result, actual buffer dimensions/format and the EGL/backend import error remain separate acceptance evidence. The timed-out boot-only hilog does not cover the abort and cannot establish absence of EGL errors.
