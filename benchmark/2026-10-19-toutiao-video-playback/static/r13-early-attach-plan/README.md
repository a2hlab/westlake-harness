# R13 earliest admissible attachment (plan only)

**Improvement: remove the feed-screenshot wait from the diagnostic attachment critical path, if the exact child and all five pinned modules already exist.** The existing observer can resume and wait for UI-driven calls. It cannot attach to a module-incomplete child and wait for modules to load. This plan makes no claim about early-exit causes or guaranteed earlier observability; there must still be an observable business process.

## What the existing code requires

- The guard is named `Guard` (`diagnostic-r13/identity.py:6`), not a separate `R13Guard` class. It checks boot/PID/birth/UID/parent, server tracer, executable hashes, and all five module paths/SHA/device/inode/maps (`:47–70`). It does **not** check feed, player initialization, or GOT. It freezes the selected module map rows; later changes refuse.
- `observer.py:41–47,164–168` checks GOT **after attach**, while stopped: player bias + `0x472688` must point to admitted android ELF `0x3b9c`, and + `0x472490` to admitted shim ELF `0x5e48`; then it installs two hardware breakpoints, resumes, and waits. The code does not require prior execution of player `init`. If slots are not yet in the expected state, it refuses; it does not resume to wait for resolution or weaken this check.
- Private `BASE20/r13_retry_outer.py:16–41` checks each child-root module file/hash/inode before attaching, but **does not check that all five are mapped**. Add that as an outer read-only prerequisite, using current exact module paths and `core.mapped_module` / `biases` semantics. File presence alone is insufficient. The existing script is unchanged and its output directory is `exist_ok=False`; reuse needs a separately reviewed fresh output/server-directory plan, not overwriting old receipts.

## One-child executable sequence for the outer

1. Before the one normal icon launch: hold the board lock, confirm baseline/rollback and exact host/server/module inputs; prepare the admitted server using the existing staging procedure. Do not spend the child's lifetime on local source hashing or document preparation. Preserve all receipts.
2. Launch the normal icon **once**. Begin a bounded readiness check (proposed at most 30 seconds, every 2 seconds, no relaunch): identify the first dedicated business child and fix boot/parent/PID/birth. Read its maps, private module SHA/device/inode and executable identity. Admit only all five exact roles (`player/android/shim/bridge/hwui`), PT_LOAD-backed mappings, one unambiguous player, and no tracer. This may run before any feed screenshot. If UI action is necessary to load a missing module, a known normal action may occur inside this same bound; do not attach expecting later loading to pass Guard.
3. As soon as the prerequisites pass, use the reviewed attach procedure with that exact identity. Start `diagnostic-r13/observe.py --admission <fresh-admission> --port 5039 --out <fresh-persistent-output> --execute` immediately after the server/admission exists. Do not insert feed/screenshot settling between spawn qualification and attach. Guard repeats the identity/maps checks; `prepare_addresses` supplies the definitive GOT gate.
4. Once existing LLDB command receipts show both exact hardware breakpoints installed and the target has resumed (confirm current non-stopped state, do not infer readiness from just two binding events), obtain the UI screenshot and perform the normal video action. Let the unmodified observer wait. Its 120-second clock starts at `Session` creation, **includes connection and guard overhead**, and does not restart after the UI action. It already accepts no-hit waiting until deadline. No new synthetic calls or function invocation.
5. Stop at the observer's event cap (4 factory + 4 lock, no pending return) or 120 seconds. Preserve partial/zero samples as unknown, run existing detach/cleanup verification, and perform the existing outer baseline restoration. Host launcher allows cleanup grace (145 seconds then SIGTERM/10 seconds); that is not extra observation time. Do not turn a timeout into a second child/window.

**Immediate stop/recovery:** child absent at readiness deadline, child changes/dies, boot/UID/parent/lock drift, missing/ambiguous modules, GOT mismatch, attach/handshake/read failure, unsupported hardware breakpoint, unexpected stop, module-map drift, or observer deadline. One child only: no fallback to software breakpoint, no repeated icon launches, no alternate process. Cleanup must prove breakpoint removal, detach, `TracerPid=0`, non-stopped state; otherwise the outer performs the approved baseline fresh-boot recovery. No playback PASS follows from diagnostic samples.
